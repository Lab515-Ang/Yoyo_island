# 棲光小島｜RiveMCP（Polymation）試用計畫

建立：2026-10-28。這份是給**新對話**用的交接文件：在隔離環境試用社群版 RiveMCP，看它能不能幫「每種體型的動物」做出待機、張望、甩尾、走路等小動作，再決定動物動態要走哪條路。

---

## 1. 背景（為什麼要試）

- 棲光小島是專注 App（React 19 + Vite + Capacitor 8，Android 實機 Galaxy A8s）。專注畫面正在改成**望遠鏡搜尋**：上方圓形鏡片在橫向全景上左右掃、推近拉遠；動物中段才在遠方出現，只在鏡頭轉開的死角換到更近的位置，時間到才走到鏡頭正前方。
  - 原型程式：`src/components/Scope.tsx`（分支 `proto/scope`）。
  - 依習性的出現方式：walk（地上）、perch（鳥類停倒木）、soar（猛禽盤旋）、eyes（貓頭鷹先亮眼睛）。
- 現在每隻動物、每個成長階段**只有一張站姿圖**，動作只能整張平移、旋轉、壓扁。想讓動物「活著」（低頭、張望、甩尾巴、跳兩步、定格走路），要決定做法。
- 已評估的方案（詳細比較見對話紀錄）：

| 方案 | 執行時負擔 | 製作成本 | 備註 |
| --- | --- | --- | --- |
| A. 一張圖＋程式動作 | 最省 | 不用另外畫 | 現況 |
| **B. 部件拆圖＋程式（CSS）動作** | 幾乎一樣省、不用套件 | 每隻多 3～5 個部件，動作手寫 | **目前建議的正式做法** |
| C. Spine 輸出 JSON | 中等（每格算骨架） | 拆部件＋綁骨架＋做動畫；要買授權（網格變形需 Pro） | |
| D. Rive | 中等，播放器比 Spine 小 | 同 C；有狀態機 | **這次要試的** |

- **省工關鍵：照體型共用骨架與動作。** 29 隻動物只有 9 種體型（`shape`：bird、owl、cat、bear、goat、mustelid、pheasant、raptor、pangolin），每種體型做 1 套動作，同體型換貼圖（Rive／Spine 叫 skin），幼年、亞成年用同一套縮小。約 9 套，而不是 29 × 3 套。

## 2. RiveMCP 是什麼（2026-10-28 檢查結果）

- npm 套件 `rivemcp`，產品改名 **Polymation**；作者 paradoxsyn（單人），2026-04-21 首次發布，檢查時最新 **1.19.0**（2026-10-26）。
- 宣稱 224 個工具：從零產生 `.riv`／`.rev`、狀態機、骨架與網格變形、**「一張圖或分層 PSD → 有骨架的角色」**、物理、Lottie／AE／Figma 互轉。
- 發布頁：https://github.com/paradoxsyn/rivemcp-releases ；授權碼：polymation.stunning.gg（沒有授權碼時有試用額度，價格未查到）。

### 安全檢查（只下載套件讀內容，沒有安裝或執行）

1. **沒有可讀的原始碼**：npm 套件只有 `bin/rivemcp.mjs`（啟動程式）和 `scripts/postinstall.mjs`。
2. **安裝時下載混淆過的原生執行檔**：postinstall 從 `github.com/paradoxsyn/rivemcp-releases/releases/download/v{版本}/rivemcp-win-x64.exe` 下載，**沒有雜湊或簽章驗證**。
3. **以使用者完整權限執行**：接上 MCP 後在背景跑，讀得到檔案、連得上網路；程式碼無法審查。
4. **專有授權、需付費**（LICENSE：RiveMCP Proprietary License）。
5. **`.riv` 由它自己從零產生**（非官方編輯器），宣稱會用 Rive 官方 runtime 驗證；Rive 改格式時可能有相容風險。
6. **權限一次放行全部**：所有工具包在 `find_tool`／`use_tool` 裡，同意 `use_tool` 等於同意全部；可設 `POLYMATION_TOOLS=core|standard|full` 改成逐一列出、逐一同意。
7. 預覽用無頭瀏覽器（Playwright 的 Chromium，沒有就用 Chrome／Edge）。

**結論：不要裝在存放專案的這台電腦上；只在隔離環境試。**

## 3. 測試環境（隔離）

- 建議 **Windows 沙箱**（Windows 10 專業版內建，關掉就全部清除）。要由使用者自己在「開啟或關閉 Windows 功能」勾選「Windows 沙箱」並重開機。
- 沙箱裡只放：
  - 測試用的一隻動物素材（見第 4 節），**不要放專案原始碼、金鑰、帳號資料**。
  - Node.js（官方安裝檔）、Claude Code 或其他 MCP 客戶端。
- 安裝（在沙箱裡）：

```json
{
  "mcpServers": {
    "polymation": {
      "command": "npx",
      "args": ["-y", "rivemcp@1.19.0"],
      "env": { "POLYMATION_TOOLS": "core" }
    }
  }
}
```

- 先不填授權碼，用試用額度；`POLYMATION_TOOLS=core` 讓每個工具都要個別同意。
- 備案：也可以直接下載發布頁的 `rivemcp-win-x64.exe` 在沙箱執行。

## 4. 測試素材

- **先試一種體型：貓科（cat）**，代表動物石虎 `leopard_cat`（專案裡已有正式圖：`src/assets/animals/leopard_cat.webp`）。
- 準備兩種輸入，比較哪個效果好：
  1. **一張完整的動物圖**（512×512 去背，側面朝右，腳底在畫布底部往上 8%）。
  2. **分層 PSD**：頭、身體、前腳、後腳、尾巴，各一層；圖層名稱用英文（head、body、leg_front、leg_back、tail）。拆圖可以請 GPT 協助，或用影像工具手動切。
- 風格：霧面黏土、低彩度；動作要安靜、療癒，不要誇張（專注 App，不能讓人分心）。

## 5. 要做出來的動作（每種體型同一套）

| 動作 | 說明 | 長度 |
| --- | --- | --- |
| idle | 呼吸、身體微微起伏 | 3～4 秒循環 |
| look | 抬頭張望、轉頭看一邊再轉回來 | 2～3 秒 |
| sniff | 低頭聞地面 | 2 秒 |
| tail | 甩尾巴一次 | 1 秒 |
| walk | 走幾步（可試「定格感」：每秒約 8 格的一頓一頓） | 1 個循環約 0.8 秒 |
| sit（選做） | 坐下 | 1.5 秒 |

- 狀態機：idle 為預設，每隔幾秒隨機切到 look／sniff／tail，再回 idle；外部可以觸發 walk。
- 加分：同一份檔案換另一隻貓科（例如西表山貓、雲豹）的貼圖，動作直接共用。

## 6. 評估標準

| 項目 | 怎麼看 | 及格 |
| --- | --- | --- |
| 動作品質 | 自然、不扭曲、關節不穿幫 | 不用大改就能用 |
| 黏土感 | 網格變形有沒有柔軟、被擠壓的感覺 | 比 CSS 方案明顯好 |
| 共用性 | 換同體型另一隻的貼圖能不能直接用 | 可以 |
| 檔案大小 | 一隻動物的 `.riv` | 越小越好，目標 < 200 KB |
| 播放效能 | 在 Galaxy A8s 的 WebView 播放（`@rive-app/canvas`），量 CPU、每秒格數 | 不卡、耗電增加不明顯 |
| 製作時間 | 從素材到可用動作花多久 | 比手寫 CSS 快 |
| 成本 | 授權費 | 可接受 |

- 效能實測方式：把 `.riv` 拿回主電腦，用 Rive 官方的網頁播放器做一個最小 HTML（不要在主電腦安裝 RiveMCP），用 `adb` 在手機上量（`dumpsys gfxinfo`、`top`）。
- 對照組：同樣幾個動作，用方案 B（部件＋CSS 動作）做一版，並排比較。

## 7. 試完要帶回主對話的結論

1. 動作品質截圖或錄影（每個動作各一段）。
2. `.riv` 檔大小、手機上的 CPU／每秒格數。
3. 實際花的時間、試用額度夠不夠、正式授權價格。
4. 建議：用 RiveMCP（D）、改用 Spine（C）、還是維持方案 B。

### 方案 B 實測結果（2026-10-28，Galaxy A8s、Chrome 156）

| 情況 | 頁面每秒格數 | Chrome 全部程序 CPU（平均／最高，單核 = 100%） |
| --- | --- | --- |
| 空白頁（基準） | — | 0.8%／11% |
| idle＋自動隨機 | 59 | 54%／131% |
| walk | — | 48%／108% |
| walk＋定格感 | — | 28%／72% |

- `top -d 1` 取樣 15 秒；手機 6 核。CPU 是 7 張半尺寸部件一直在動的成本，量 Rive 時用同樣方法比。
- 定格感（`steps(2)`）CPU 幾乎減半：畫面不變的格數不用重畫。
- **第一版部件有破綻**：GPT 把關節畫成玩具插銷／插槽（米白圓柱），身體也有洞，每個動作都看得到。已用「關節處全是毛皮、四肢上端延伸成圓頭」重畫（`.forge/rive-test/parts2/`），組裝改成**四肢、尾巴、頭都在身體後面**，由身體輪廓蓋住所有接合處（`out2/leopard/`）。B 頁面與沙箱 PSD 已換新；放大檢查過靜止、look、sniff、tail 兩端、walk 四個階段，沒有接縫。
- 拆圖提示的教訓：不要寫「joints」「rounded ends where limbs attach」這類字眼，GPT 會畫成玩具接頭；要明寫「no pegs, sockets, holes, cut faces」和「fur-covered extended ends that tuck behind the body」。
- 去背的教訓：白底去背後邊緣 1～2px 混了白色，部件疊在深色部件上（西表山貓最明顯）會變成一圈白邊接縫。現在遮罩先往內縮 2px 再柔化；石虎、西表山貓（`out2/iriomote/`）、單張側面圖都已重切，沙箱素材已換新。

### 骨架拆圖（2026-10-28，第三版）

前兩版（GPT 分開畫部件）有玩具接頭、圖層順序反、腿和尾巴只有一片、頭沒拆、沒有階層，已作廢。第三版做法（腳本都在 `.forge/rive-test/rig/`）：

1. **剝層**：以正側面主圖為參考，請 GPT 各做一張只改一處的編輯圖：去近側兩條腿（E1）、去四條腿（E2，肚子被畫胖，最後沒用）、去頭（E3）、去兩隻耳朵（E4）、閉眼（E5）。`register.py` 用 OpenCV ECC 對齊（位移都 < 1.5px）並校正色調。
2. **找範圍**：主圖與編輯圖逐像素比差異 → 近側腿、遠側腿、頭、耳朵、眼睛的範圍（`masks.py`）。差異範圍有碎片，腿另外用肚子線、開運算、手畫的腳掌輪廓修乾淨。
3. **切部件**（`rig.py`）：看得到的像素一律用主圖，被擋住的才用編輯圖；相鄰部件在內部接縫互補、硬邊。每個關節的父段、子段都含「以轉軸為圓心、半徑＝該處半寬」的圓盤，切線垂直於腿或尾巴的方向，子段再往父段底下多伸 6px。髖、肩圓盤羽化 24px 融進身體。頭的轉軸在後腦（點頭時後腦不動）。
4. **檢查**：`pose.py` 離線擺姿勢合成；`check_poses.py` 把 look、sniff、張嘴、眨眼、甩尾兩端、走路兩個極端放大檢查；靜止時與主圖平均差 1.5（只在外輪廓內縮的去白邊）。PSD 合成也比對過。
5. **輸出**：`make_psd.py` → 有群組的 PSD；`make_b.py` → 巢狀 B 頁面。縮圖要用 BOX，Lanczos 在硬邊會振鈴出一圈亮線。

**網格版（2026-10-28）**：硬切片的關節一定會錯開花紋、耳根和脖子會裂，這是做法本身的上限（CSS 只能整塊轉，做不到網格）。所以另外輸出 `leopard_cat_mesh.psd`（`make_mesh.py`）：每條腿、尾巴、身體＋脖子各合成一塊，耳朵、頭、眼皮、下巴分開；附 21 根建議骨頭。沙箱任務說明把網格變形改成必測，寫了每塊圖層綁哪些骨頭、關節兩側 30～50px 權重漸變、要截圖的 5 項檢查。

做網格版時又找到並修掉硬切片的三個錯（B 頁面已一併更新）：
- **兩隻耳朵在遮罩裡連成一塊**，`ear_near`、`ear_far` 兩個圖層都含兩隻耳朵，耳朵一動就分裂。改成手描耳朵和頭、脖子、另一隻耳朵的交界線（差異遮罩太雜，不能用）。
- 頭本體在耳朵邊緣有一圈透明縫，耳朵一轉就露出來。
- 脖子在耳朵位置取到主圖的耳朵像素，低頭時頭後面出現「鬼耳朵」；改成那裡只取去頭圖，缺口用閉合補平、顏色 inpaint。

**網格權重播放器（2026-10-28）**：為了在 Rive 之前先確認「網格權重能不能真的解決」，自己寫了 WebGL 網格播放器 `player\m\`（`http://localhost:5180/m/`，`make_mesh_player.py` + `m_template.html`）：12 個圖層切成每 12px 一格的三角網格（共約 8,000 頂點、14,700 三角形），每個頂點最多 4 根骨頭的線性混合蒙皮，動作和 B 頁面相同（idle、look、sniff、tail、walk、定格感）。檔案約 500 KB（網格資料以 base64 內嵌，可再壓）；桌機 60 fps，手機還沒量。`mesh_pose.py` 是同一套數學的離線渲染器，檢查用。

權重設計：
- **脊椎場**：只分 body、head 兩根；按「離身體核心」和「離頭」的距離比例漸變，再柔化 20px。身體＋脖子、頭、眼睛都用同一個場，所以疊在一起的地方權重一樣、一起變形，脖子整段平順地彎。
- 腿、尾巴、下巴：沿自己的骨頭鏈量距離，每個關節前後 18～45px 漸變；第一段從脊椎場漸變出來，所以腿根和身體黏在一起。
- 耳朵：按「離看得到的頭皮多遠」漸變（近側 70px、遠側 40px），耳根整條邊黏在頭上。
- 網格版專用的脖子圖層：頭底下只取去頭圖的自然脖子（硬切片版為了蓋縫墊的那塊會在低頭時露出直邊）。
- 遠側耳朵被近側耳朵擋住的部分往後延伸補畫，近側耳朵擺動時不再露白。

結果（`compare_rig_mesh.png`，左硬切片、右網格）：低頭 13°＋脖子 6°、耳朵 -8°／+5°、走路大腿 ±6°／小腿 ±12°，網格版都沒有裂縫、花紋連續拉伸。沙箱已附 `leopard_cat_mesh_weights.json`（每個頂點的權重）給 RiveMCP 匯入或比對。

硬切片的已知限制（網格版已解決）：
- 兩隻耳朵互相擋住的部分沒有畫面可補，各自轉超過約 4° 中間會露白；B 頁面耳朵抽動收到 -4°、張望時耳朵只多轉 -3°。
- 關節轉動時圓盤邊緣的斑紋會錯開一點（膝蓋那顆斑點最明顯）；髖、肩圓盤轉太多會糊，所以大腿只轉 ±4°。
- 頭頸交界：抬頭時喉嚨有淡淡的直邊、低頭時耳後有一個小缺角，原尺寸約 3～5px（手機上不到 1px）。脖子本身硬轉會露縫，B 頁面不轉脖子。

### 網格版走路破綻的修正（2026-10-28）

使用者在手機上看網格版走路，大腿和脖子還有破綻。之前的檢查是用原尺寸貼圖離線渲染，看不到手機上半尺寸貼圖才出現的問題；`mesh_pose.py` 加了 `HALF=1`（用跟手機一樣的 webp、先預乘再內插），`walkcheck.py` 裁跟手機截圖一樣的範圍。找到並修掉：

1. **身體被腿的小腿、腳掌帶著剪切**：身體在腿根附近的權重原本照整條腿的鏈算，小腿一彎，身體的肚皮也被拉歪，前腳上方出現水平斷層。改成身體只跟大腿那根（`leg_upper_only`）；腿圖層在壓著身體的地方用一樣的權重，離開身體 40px 內才接上整條鏈。
2. **腿根、尾巴根「全跟」的範圍太小**：改成大於「腿和身體重疊處離轉軸最遠的距離」（後腿 175、前腳 155、尾巴 99px）。
3. **遠側腿的圓盤帶著 E1 補畫的肚皮一起轉**：E1 的肚子比主圖胖、顏色偏白，走路時從前腳後面甩出一塊淺色方塊。遠側腿只取主圖也有東西的範圍，往肚子線上方延伸 25px 藏在身體後面；看得到的地方改用主圖像素（靜止時與主圖平均差從 1.5 降到 1.17、p99 從 24 降到 8）。
4. **近側腿圓盤挖掉肚子線以下的楔形缺口**，縮成半尺寸後缺口邊緣透出底下肚皮的線；近側腿圓盤改成整片保留。
5. 身體肚子線以下不再切水平直線，改用主圖自然輪廓扣掉腿；頭邊緣內側 8px、耳根內側 6px 的底下保留主圖像素（半透明邊緣底下要是同樣的像素）。
6. `make_mesh.py` 每層往「靜止時被上層完全蓋住」的地方多延伸 10px。

7. 遠側腿往身體後面延伸的那段，原本取到身體的奶油色肚皮，腿往前擺時露出一撮淺色；改成沿用最近的腿本身顏色。

### 硬切片 vs 網格 實測（2026-10-28，Galaxy A8s、Chrome 156）

同上面方案 B 的量法（`top -d 1` 取樣 15 秒、Chrome 全部程序 CPU 加總、單核 = 100%；每種情況量完截圖確認按鈕狀態）。B 是骨架版 23 個部件、巢狀 CSS；網格是 WebGL、12 層約 8,000 頂點。

| 情況 | B 硬切片（CSS） | 網格（WebGL） |
| --- | --- | --- |
| 空白頁（基準） | 1.2%／19% | — |
| idle＋自動隨機 | 52.5%／115% | 55.9%／124% |
| walk | 81.0%／169% | 68.0%／138% |
| walk＋定格感 | 50.8%／104% | **35.3%／76%** |

（平均／最高）
- 兩版頁面上的計數器都是 60 fps。這個計數器量的是 requestAnimationFrame 的次數，只能說明主執行緒沒卡住，量不到合成器掉格；肉眼看兩版走路都順。
- idle 兩版差不多；走路時網格版比 23 個 CSS 部件還省（CSS 每塊骨頭都是一層合成圖層，走路時十幾層同時在動）。
- 定格感在網格版最有效：每秒只畫 8 次，畫面沒變的格數完全不畫（CSS 的 `steps()` 只省一部分）。
- 舊的 7 片 CSS 版走路是 48%：部件從 7 片變 23 片，CSS 版走路成本變成 81%。
- 量的過程中發現 B 頁面的 bug：骨頭 div 是滿版的，走路時旋轉會蓋住右側按鈕，「定格感」按不到；已加 `pointer-events: none` 修好（第一次量的 B 版 walk＋定格感數字因此作廢重量）。
